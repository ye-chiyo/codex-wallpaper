# 素材库缓存与 File 交接优化

## 素材库索引

原先默认项目索引在 5 秒后失效，下一次选择会同步重新发现 Steam 库并枚举全部项目。实测本机冷枚举约 125–133 ms。

现在每次选择直接使用已有项目索引。超过 5 秒复核窗口时，调用方仍立即取得旧索引；后台只计算现有扫描签名。签名不变时仅更新检查时间，不读取项目目录。根目录或 `visibility.json` 变化时后台重扫并替换索引。为避免已有项目内 `project.json` 的改动永久不可见，每 5 分钟最多执行一次后台完整复核。`DSH_WE_STEAM_ROOT` 改变会立即使旧索引失效。

实测：

| 场景 | 耗时 |
| --- | ---: |
| 首次冷扫描 | 125.4 ms |
| 超过 5 秒复核窗口后的调用 | 2.0 ms |

缓存不会跳过每次选择时的实际文件校验。媒体文件会重新 `stat`，路径仍按真实根目录检查，删除或不可读会走既有失败路径。

## File 交接

原先每个 File 资产需要：

1. 创建隐藏输入并取得 token。
2. `DOM.getDocument`。
3. `DOM.querySelector`。
4. `DOM.setFileInputFiles`。

现在由一次 `Runtime.evaluate` 返回该输入元素的 `objectId`，直接传给 `DOM.setFileInputFiles`。不再获取或查询整棵 DOM 树。

第一版替换把查询表达式的引号多转义了一层。宿主在 `object-query-start` 后立即 `deliver-failed`，随后对《鸣潮》今昔静默退回完整 Base64 传输。旧测试夹具直接把 false 结果当作成功 objectId，没有解析宿主生成的 JavaScript，因此未发现该错误。

修正后，查询表达式可被 JavaScript 正常解析，夹具也会先解析表达式再返回 objectId。当前真实监督进程 56188 的 4K90 →《鸣潮》今昔切换：

| 项目 | 错误回退时 | 修正后 |
| --- | ---: | ---: |
| 新播放器创建 | 3179.0 ms | 64.6 ms |
| 进入当前画面层 | 3381.3 ms | 258.2 ms |
| 完整 Base64 分块 | 有 | 0 |

修正后视频为 `readyState=4`、未暂停、4680×2160、无媒体错误。剩余时间主要是真实首帧解码与呈现；本次优化没有改变素材、解码器或画质。

## 验证

`pnpm test`：41/41 通过。新增回归验证过期索引先返回旧数据，后台在扫描签名变化后加入新项目并更新已有项目元数据；宿主夹具会实际解析 `Runtime.evaluate` 表达式，避免错误 objectId 查询被当成成功。既有测试继续验证 objectId 释放、大于 512 MiB 的视频不进入 Base64，以及 File 输入对象缺失时的安全回退。

真实页面已恢复原运行时、原壁纸和配置，窗口及监督进程保持运行。
